# M2: full-token decode is correct (both models), file-backed weights

**Gate: passed on Ornith-1.5-35B-A3B and Qwen3.6-35B-A3B against the native-layout
llama.cpp** (same commit and kernels as the engine, KleidiAI off; see M1.md for why that is
the reference). Every logit row of every evaluated position is **bit-identical**, so KLD is 0
and top-1 agreement is 100%. That covers 256-token greedy runs on three prompts per model plus
corpus chunks, and holds at 4, 6 and 8 threads, packed or spread. Decode speed with the real
math is for Codex to measure (commands below); it was not timed here.

Ornith is numerically chaotic. One ulp anywhere in the network grows to O(1) logit
differences through 40 layers of top-8 routing; M1's ssm_conv bug did exactly that. So:
- "identical tokens vs llama.cpp" is meaningful only against the *same computation*. oxe
  meets it against the native-layout build.
- A KLD <= 1e-5 gate against a *batched* llama.cpp base, or against production KleidiAI,
  cannot be met by any implementation that does not replicate that exact path. llama.cpp
  fails it against itself (0.027).
- **Decision for the owner:** to be token-identical with the *production* server, oxe would
  have to implement KleidiAI's per-row int8 path for Q6_K/Q8_0/dense Q4_K (more bytes per
  token: the head becomes 0.51 GB instead of 0.417 GB native). The alternative is to treat
  the native-layout llama.cpp as the reference; its distance to production is the same
  ~0.006 KLD as oxe's.

## Item 4: memory (file-backed repacked weights)

Design (`crates/model/src/weights.rs`):
- **First load of a model:** the plan's tensors are repacked in parallel straight into a
  `MAP_SHARED` mapping of `<model-sha256>-<engine-id>.bin.tmp.<pid>` under
  `~/.cache/local-ai/snapdragon-engine/` (dir 0700, files 0600, `O_NOFOLLOW`, owner check).
  The token embedding and F32 tensors are copied too, so a warm load never opens the GGUF.
  Per (tensor, expert) item, the source range is `MADV_DONTNEED`ed. When a tensor completes,
  its file pages are `POSIX_FADV_DONTNEED`ed. Then: header with per-tensor checksums, `msync`,
  `fsync`, `rename`, and a dir fsync. The written pages are dropped and every checksum is
  verified by reading the file back from disk ("verify once at write").
- **Later loads:** header check (magic, engine id, model sha256 + size, file length, header
  checksum, entry-by-entry layout match against the plan), then `mmap` read-only and verify a
  random sample of 8 tensor checksums (`--verify full|none` to change). The GGUF is not touched.
- Model identity: sha256 of the GGUF via `sha256sum` (~2.3 GB/s here), computed once and
  remembered in `sha256-index.tsv` keyed by (dev, inode, size, mtime, ctime);
  `OXE_MODEL_SHA256` overrides. Engine id: `w1-ee6b9a1-<hash of kernel cflags>`. Stale
  files after a layout/engine-id change are not reused; delete them by hand (one per model
  is kept today: Ornith 16 GiB, Qwen3.6 21 GiB).

| Measurement (VmHWM etc. from /proc/self) | Ornith | Qwen3.6 | M0 (Ornith) |
|---|---:|---:|---:|
| arena (cache file) | 15.66 GiB | 20.84 GiB | 15.4 GiB anon |
| cold build: time (8 load threads) | 18.9 s + 3.5 s verify (+ one-time sha256) | 13.3 s (4 threads) + 4.9 s verify | — |
| **cold build: peak VmHWM** | **15.43 GiB** (RssAnon 18 MiB; the rest clean file pages) | — | 27.42 GiB |
| warm load | **0.05-0.09 s** | 0.05 s | 5.16 s |
| warm, after 69 decoded tokens: VmHWM / RssAnon | 7.04 / 0.16 GiB (only touched experts are resident) | 8.81 / 0.16 GiB | — |

Steady-state RSS approaches the arena size once most experts have been touched. All of it is
clean, reclaimable file cache except ~0.2 GiB (KV, recurrent state, scratch). This sits well
under the 28 GiB cap, and Qwen3.6 fits too.

**THP:** the cache lives on btrfs, and this kernel has no `CONFIG_READ_ONLY_THP_FOR_FS`, so
file-backed mappings get no PMD huge pages (`FilePmdMapped = 0`; `--thp-collapse` tries
`MADV_HUGEPAGE` + `MADV_COLLAPSE` anyway). arm64 contiguous-PTE folios may still help the
TLB; unmeasured. `--weights anon` copies the arena into an anonymous `MADV_HUGEPAGE` region
(M0's configuration: +15.7 GiB anon) for the A/B. **If file-backed decode turns out slower,
that A/B decides the default.** A `MAP_HUGETLB` arena would need reserved hugepages: not
pursued.

## Item 5: prefill

M2 prefill runs token by token through the decode path. It is exact and runs at decode
speed (~30-40 tok/s): fine for the gates, too slow for 7K-token cold prompts. Plan (M3.2, next):
1. **Batched GEMM path for prompt chunks** (e.g. 64-512 tokens): the same repacked layouts
   with ggml's `ggml_gemm_q4_K_8x8_q8_K` / Q3_K i8mm GEMM from `claude/q3k-moe-gemm` (vendor
   via extract.py), q8_K activation tiles via `ggml_quantize_mat_q8_K_4x8`, MoE grouped by
   expert like `forward_mul_mat_id` (rows per expert, >= 4 rows -> GEMM).
2. **Chunked gated delta net** for the recurrent layers (`ggml_gated_delta_net` with n_tokens > 1,
   the fused-CH path) and FA-off attention over the chunk with the causal mask.
3. Exactness target for prefill: the batched path cannot be bit-identical to the decode path
   (llama.cpp's own batch-vs-decode KLD is 0.027 on Ornith). The reference for the prefill
   path is llama.cpp's batched prefill (`dump_ref --batch`). Gate: KLD vs that, plus
   decode-after-prefill identity with llama.cpp given the same prefill.
4. Alternative from SPEC B.7: run prefill in llama.cpp and import its state; the
   snapshot/restore API below is the import point.

## Server integration (from the server lane's request)

- `Engine::save_recurrent()` / `restore_recurrent()`: conv + delta-net state + position, 62.8
  MiB (Ornith); KV stays in place, and restore zeroes V^T past the restored position. Unit
  test: restoring and replaying gives bit-identical logits.
- `model::load::open_static` (leaked plan + weights) -> `Engine<'static>`.
- `sched::DetachedPool`: the pool's own leader thread is worker 0, so the server's blocking
  threads can submit tokens. `Engine::step` takes any `sched::Team`.
- `crates/server/src/oxe_engine.rs`: `OxeEngine` implements the server `Engine` trait.
  `oxe-server --engine oxe --oxe-cpus 0,1,2,4,5,6,8,9 --model <gguf>`. Smoke test:
  `/completion` "The capital of France is", greedy 16 -> " Paris. Paris is the largest city
  in France and is located in the north-central", token ids identical to the oracle.

## Commands for Codex's speed re-run (correct math)

The gate: at most 24 ms/token, ideally lower, with identical output. All runs need the lease and llama-server stopped.

`$MODELS` is the directory that holds the GGUF files.

```bash
cd <repo> && git pull && CARGO_BUILD_JOBS=2 cargo build --release
# (weight caches already exist: Ornith 16 GiB, Qwen3.6 21 GiB; a new engine id rebuilds once, ~20-40 s)

# 1. the M0 gate configuration, real math (spread was M0's winner: 23.16 ms)
tools/run_bench.sh --cpu-list 0,1,2,4,5,6,8,9
# 2. packed
tools/run_bench.sh
# 3. weights in an anonymous THP arena instead of the file mapping (M0's layout)
tools/run_bench.sh --cpu-list 0,1,2,4,5,6,8,9 --weights anon
# 4. per-phase work/wait table (adds timestamps; compare with 1 for overhead)
tools/run_bench.sh --cpu-list 0,1,2,4,5,6,8,9 --profile
# 5. Qwen3.6
MODEL=$MODELS/Qwen3.6-35B-A3B-MTP-UD-Q4_K_M.gguf tools/run_bench.sh --cpu-list 0,1,2,4,5,6,8,9
```

`run_bench.sh` runs `oxe bench --ctx 2048 --prompt-len 16 --tokens 128 --warmup 16`. That is a
fixed 16-token prompt (token by token), 16 warm-up decode tokens, then 128 timed greedy
tokens. It writes `results/bench-*.json` with `ms_per_token.{median,mean,min,p90}`, `tok_s`,
`barriers_per_token` (plan: 211), `generated_ids` + `generated_hash`, `load` (cache
hit/backing), `memory_kb` (VmHWM, RssAnon/File, AnonHugePages, FilePmdMapped) and `profile`.

**Identical output:** every arm of one model must print the same `generated_hash` (the
math is thread-count and backing invariant). To tie a bench arm to llama.cpp, run
`./target/release/oxe verify --model <gguf> --ref ~/.cache/local-ai/snapdragon-engine/oracle/ornith-p1-code --cpu-list <same list>`.
It must print `"greedy_identical": true` and 308 bit-exact rows. It takes ~10-20 s, and the
logits copy and KLD make it no timing run.

Expected costs vs M0 (23.16 ms spread), for interpreting the result:
- +40 barriers/token (211 vs 171, ~+0.03 ms).
- MoE down: full-K per expert by output rows (better balance than M0's split-K LPT;
  idle should drop).
- f32 router via `ggml_vec_dot_f32`. Attention pads to 256 positions minimum (llama.cpp
  does too).
- Kernels are now built with llama.cpp's `-march=armv8.6-a+...` instead of
  `-mcpu=oryon-1`: same results, possibly different scheduling.
- File-backed weights without THP (item 4): compare runs 1 and 3.

## Remaining gaps

1. **Speed is unmeasured with the real math** (Codex lane, commands above). If it misses
   24 ms, the first suspects are the file-backed TLB cost (A/B with `--weights anon`), the
   oryon-1 vs armv8.6-a kernel flags, and the redundant per-thread activation quantisation
   (`quantize_row_q8_K_ref` is scalar; it runs per thread for x, o and h).
2. Production identity needs the KleidiAI path (decision above). The native path is exact.
3. Batched prefill (item 5) and MTP (next speed lever; verify path must stay batch-invariant).
4. The determinism soak (10K tokens) and Codex's production corpus (8x512 against the
   production base) are not run. The decode path is bitwise thread-invariant by construction
   and by test, so the soak is low risk.
5. Stale-cache cleanup is manual (one file per model/engine id).
