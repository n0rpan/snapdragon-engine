# M0: roofline probe (timing-only plan runner)

M0 is the kill test in the design spec, section B.10 (kept in the development notes, not in this repo).
It answers one question before any model math is written: **with the real Ornith weights,
the real vendored kernels, the planned work partitioning and only ~171 barriers per token,
how fast can one decode token go on this laptop?**

The runner executes the static per-token plan for all 40 target layers and the output head:
every GEMV over the real repacked weights, the MoE routed to the real top-8 count, delta-net
state and attention KV moved with the correct byte volumes. Activations are dummy (bounded
values derived from real ops); **numerics are not checked in M0**, only time, barriers and bytes.

## Build and test

```bash
cd <repo>
cargo build --release            # .cargo/config.toml sets jobs = 1 and target-cpu = oryon-1
cargo test --workspace           # 26 tests, RUST_TEST_THREADS=1, ~3 s; synthetic data only,
                                 # plus header-only checks of the two model files if present
```

Toolchain: `/usr/bin/cargo`, rustc 1.99.1, gcc 16.1. Dependencies: `memmap2`, `libc`, `cc`,
`serde_json` (CLI and tests only). The vendored C/C++ kernels are compiled with the pinned
llama.cpp CPU flags `-O3 -DNDEBUG -mcpu=oryon-1+rng+crc+nopauth+dotprod+i8mm+nosve+nosme
-U__ARM_FEATURE_SVE -U__ARM_FEATURE_SME` (see `vendor/ggml-subset/PROVENANCE.md`).

## The command for Codex (gate run)

Preconditions (Codex lane):
1. memlat boot (the gate numbers are relative to the same-boot llama.cpp baseline);
2. the inference lease taken (an optional inference lock file, `$LOCAL_AI_LEASE`) and **llama-server
   stopped**: M0 repacks Ornith into a 15.4 GiB anonymous arena (THP-advised) on a 30 GiB
   machine, on top of the file's page cache;
3. otherwise quiet machine, 8 packed cores.

One command:

```bash
cd <repo> && tools/run_m0.sh
```

It builds if needed and runs exactly:

```bash
./target/release/m0-timing --threads 8 --cpu-list 0-7 --ctx 2048 --tokens 128 --warmup 16 \
    --experts random --out results/m0-<timestamp>.json
```

It prints one summary line to stderr (ms/token, tok/s, barriers/token, ns per empty barrier,
effective GB/s, speed-up vs llama.cpp, verdict) and the full JSON to `results/`
(git-ignored). The load (read + repack of ~16.2 GB, 8 threads) prints progress per GiB;
**its duration has not been measured** (rough guess 30-90 s, Q3_K repack is scalar C).

Suggested follow-ups, one run each, same lease (pass flags to `tools/run_m0.sh`):

| Purpose | Extra flags |
|---|---|
| Profiling overhead A/B (timestamps around every kernel call and barrier) | `--no-profile` |
| Real router top-k instead of random experts (expert locality) | `--experts router` |
| Same experts every token (upper bound, page-cache-like locality) | `--experts fixed` |
| Spread over the 3 clusters (SPEC grey-zone rule) | `--cpu-list 0,1,2,4,5,6,8,9` |
| 16K context (KV 0.336 GB/token instead of 0.042) | `--ctx 16384` |
| ns/barrier table, packed 4/6/8/12 (SPEC B.12 #2) | `./target/release/barrier-bench` |
| Drop the file's page cache as it is repacked (memory pressure) | `--drop-file-cache` |

`m0-timing --help` lists every option. `--synthetic zero|fill` and `--layers N` exist for
smoke tests; such runs report `verdict: n/a`.

## What the gate numbers mean

| | Value | Meaning |
|---|---|---|
| Baseline | **31.16 tok/s ≈ 32.1 ms/token** | same-boot patched llama.cpp (acd47 build), Ornith, 8 packed threads (`-C 0xff --cpu-strict 1`), MTP off |
| **GO** | **median ≤ 24 ms/token and ≤ 200 barriers/token** | ≥ 41.7 tok/s, ≥ 1.34x baseline: worth building M1-M3 |
| **STOP** | **median > 27 ms/token** | ≤ 37 tok/s: even an ideal schedule cannot reach the M3 gate (≥ 1.15x = 35.8 tok/s) once real math is added; the llama.cpp patch path stands |
| Grey | 24-27 ms | run the other layout once (spread cpu list; two-phase MoE is not implemented in M0, see open questions), then decide |

Bytes per token in this plan (unique DRAM traffic, from the plan, asserted in tests against
`model_inspect.py`): **weights 1.7970 GB** (exactly model_inspect's `active_bytes_per_token`:
dense incl. the native-Q6_K head and shared experts, routed experts at 8/256) **+ recurrent state
r+w 0.1317 GB + KV at 2K 0.0420 GB = 1.9707 GB/token**. That is lower than the 2.09 GB in
SPEC §1.2 because the head and shared experts stay native Q6_K here (llama.cpp expands them
through KleidiAI int8). Hence:

- 24 ms/token ≙ **82 GB/s effective** (the SPEC's "87 GB/s" assumed 2.09 GB);
- the ideal at the 108 GB/s 8-packed read ceiling is 18.2 ms/token (54.8 tok/s).

`gb_s_effective` in the JSON = `bytes_per_token.total_unique / median`. `kernel_streamed` is what
the kernels actually read (it is ≥ the unique total: two threads share each 8-row group of
`ssm_beta`/`ssm_alpha`, and attention counts each KV head once per q-head group).

## Output fields (JSON on stdout)

- `ms_per_token.{median,mean,min,p90,stdev}`, `tok_s` (from the median), `per_token_ms`.
- `barriers_per_token` (measured from the barrier's episode counter) vs `barriers_per_token_plan`
  (171 for Ornith); `barrier_ns_empty` (2000 empty barriers on the same pool before the run).
- `bytes_per_token.*`, `gb_s_effective`.
- `gate.{verdict, speedup_vs_baseline, ...}`.
- `profile.phases[]`: per phase kind, per-thread mean `work_ms` and `wait_ms` (barrier wait) per
  token, `idle_pct`. `profile.kernels[]`: per kernel class, mean thread time per token, GB/token
  streamed and the resulting GB/s while running; compare with the [M] figures in SPEC B.10
  (Q4_K 91, Q3_K 81 GB/s in llama.cpp).
- `load.seconds`, `load.arena_bytes`, `kernel_cflags`, `engine_commit`.

## The plan that runs (Ornith, 8 threads)

| Phase (per layer) | Per-thread work | Barrier after |
|---|---|---|
| `deltanet_mix` (30 layers) | x += MoE partials of the previous layer (redundant, all threads); RMSNorm + q8_K quantise (redundant); `attn_qkv` rows of its 2 key heads (q, k) and 4 value heads (v), `attn_gate` (z) rows of its value heads, the 8-row `ssm_beta`/`ssm_alpha` groups covering them; conv1d + SiLU on its channels (conv state r+w), l2norm, delta rule on its value heads' 128x128 f32 states (one read + one write), gated RMSNorm | B1 |
| `deltanet_out` | quantise the 4096-wide mixer output (redundant), `ssm_out` own 256 rows, residual into x1 | B2 |
| `attn_qkv` (10 layers) | combine + norm + quantise; `attn_q` rows (q and gate) of its 2 query heads, q-norm, partial rotation; its 64 rows of K and of V, written f16 into the cache at the new position | B1 |
| `attn_core` | its 2 query heads over all `n_kv` cached positions (f16 K/V, f32 softmax), sigmoid gate | B2 |
| `attn_out` | quantise 4096, `attn_output` own rows, residual into x1 | B3 |
| `moe_router` | copy x1, norm + quantise (redundant); F32 router rows (32 of 256); shared-expert gate dot (redundant) | B3 / B4 |
| `moe_experts` | select 8 experts (random/fixed/router), build 18 split-K units (8 x 2 routed + 2 shared halves), LPT by bytes (identical on all threads, no communication), run own units: gate + up rows of the half, SiLU*up, quantise one q8_K block, down over all 2048 rows with that k-block, scaled into its private partial | B4 / B5 |
| `head` (once) | combine, output norm + quantise, native Q6_K 8x8 GEMV over its 31,040 rows in 256-row chunks with a running argmax | join |

**171 barriers/token** = 30 x 4 + 10 x 5 + 1 (head join), independent of the thread count
(asserted for 1, 2, 4, 6, 8, 12 threads). The SPEC's "B5" (x2 complete) is removed by doing the
MoE combine redundantly on every thread at the start of the next phase (each thread sums the 8
partial buffers, 64 KB, from peers' caches); that trades one barrier per layer for a few
microseconds of L2 traffic. The pool's "go" signal at the start of a token is a one-way release
and is not counted as a barrier.

Weights: Q3_K experts in our q3x8 layout (`claude/q3k-moe-gemm`), Q4_K/Q6_K in ggml's 8x8
layouts, repacked once at load into one anonymous arena (`MADV_HUGEPAGE`); FFN down weights
(routed and shared) are reordered split-K so a unit is one contiguous `n = 256` GEMV; F32 tensors
copied; the token embedding is read from the file mmap (16 prefaulted rows, no I/O in the loop).

## Faithful vs approximated

| Faithful | Approximated (M0 only) |
|---|---|
| Every weight byte of a decode token, read once, by the real kernels (`ggml_gemv_{q3,q4,q6}_K_8x8_q8_K` from llama.cpp ee6b9a1) | activations are dummy; logits and argmax are meaningless |
| Work partition: head-aligned delta-net, row-split GEMVs in 8-row groups, split-K MoE units with LPT | expert choice: random by default (top-k count real; `--experts router` uses the real router on dummy activations) |
| Recurrent state read + write in place (62.8 MiB), KV read over `--ctx` positions + one position written | conv/delta-rule/attention math is a plausible stand-in (same loops and volumes, not ggml's op order) |
| q8_K activation quantisation with ggml's own function (redundant per thread, as planned) | K-norm/RoPE on the new K row are skipped; q-norm/rotation done on q |
| Barrier structure, persistent pinned pool, zero allocation in the token loop | token embedding: raw bytes of a real row, no dequantisation |

## Open questions (for the M0 report)

1. **Load time and peak memory are unmeasured** (no real repack was run in the Claude lane; the
   load path is tested end to end on a tiny synthetic GGUF and on the first 8-row group of one
   real tensor per quant type).
2. **MoE balance**: 18 units over 8 threads; the 2 shared-expert units (Q6_K) are 1.9x a routed
   Q3_K unit, so LPT leaves ~18% imbalance in `moe_experts`. The SPEC's `two-phase` schedule is
   not implemented; `profile.phases[moe_experts].idle_pct` will show the cost.
3. **Qwen3.6 cannot run in M0**: it needs Q8_0 (dense, shared experts) and Q5_K (expert down)
   kernels (`ggml_gemv_q8_0_4x8_q8_0` + `quantize_row_q8_0`, `ggml_gemv_q5_K_8x8_q8_K`). Its byte
   accounting is already in the plan and tested (2.6262 GB weights/token).
4. **Redundant activation quantisation** (scalar `quantize_row_q8_K_ref`, which is also what
   llama.cpp uses on ARM) runs 3-4 times per layer per thread; it shows as `norm_quantize` in the
   kernel table. A NEON version that is bit-identical is a cheap later win if it matters.
5. **Profiling overhead**: timestamps (`cntvct_el0`) around every kernel call and barrier,
   roughly 1-2k per thread per token; run once with `--no-profile` to confirm it is noise.
6. **THP**: the arena is `madvise(MADV_HUGEPAGE)` and THP is `always` on this kernel; worth
   checking `AnonHugePages` in `/proc/<pid>/smaps_rollup` during a run (SPEC B.12 #5).
7. `model_inspect.py --json` does not print the tensor table; the parser fixtures take the
   table from its built-in parser (`parse_builtin`) plus the `--json` summary fields
   (`tools/gen_fixtures.py`).
